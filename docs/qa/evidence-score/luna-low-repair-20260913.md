# API Luna low：结构修复与验收

最终代码使用 `resume_review_prompt_v13`、`resume_review_openai_shape_v7`，本地模型仍为 `gpt-5.6-luna / low`。同一份合成简历的最终请求用时 **66.278 秒**，返回 **5 条建议、0 条禁用**；原生 JSON schema、服务端 schema、业务归一化及前端报告归一化均通过。

这是一次最终版本的完整 API 验收，不能据此认定跨简历稳定或整体审查质量达标。报告中的 39 分是对合成简历的评分，不是模型质量得分。未提交、推送、部署或操作真实账户。

## 本轮修复

- 请求限定主要经历为当前 `experience` 对象；对象、操作、关联经历、课程/排序选项均来自当前输入目录，不能把字段路径当选择项。
- 所有 `sourceRefs`（包括维度、亮点、建议和事实缺口）通过共享枚举限定为真实可见引用，兼容 schema 中间接的 `$ref`；JD 引用保持独立，无 JD 时必须为空。
- 已提供求职方向时，原生缺口枚举排除 `target_role`。是否缺少 JD 与是否缺少方向分开处理。
- 提示词明确候选技能字段只用于创建技能，禁止参考改写、数字占位和理想答案；强调已有事实整理不重复追问、不重复创建已有工具。
- 新生成的事实确认类方案，其方向和执行步骤由已校验的缺口类型及中性问题模板生成；保留对象名称与原文支持的指标提示。技能文字继续沿用已有程序策略。模型仍提供问题判断，程序不添加事实、改分或授予无需确认的改写权限。
- 已存报告保留原策略；已有事实的 `organize` 方案保留模型的组织建议。服务端继续拒绝坏报告、禁用不合法的单条建议，不增加模型审核、修复、重试或回退调用。

原生 schema 约束地址和选项集合；操作与参数之间的关联、证据作用范围、排列唯一性、候选技能是否为原文片段等，仍由服务端检查。没有把全部业务规则搬进提供方 grammar，也没有通过过滤旧响应的非法 ID 来制造成功结果。

## 全部实际请求记录

每轮使用同一份合成输入，均为单独的一次请求，模型回显 `gpt-5.6-luna`、档位 `low`。不同版本之间不是重复抽样，不能合并计算稳定成功率。

| 版本/试验 | 耗时（秒） | 原始建议数 | 实际结果 |
|---|---:|---:|---|
| 修复前，shape v1 | 59.975 | 6 | 主要经历含技能、教育及总结，正文携带非法选择项，整份拒绝 |
| 完整操作联合 schema，v2 | 40.949 | 0 | 格式/业务通过，但只有点评没有方案，质量失败 |
| 联合 schema 调整字段顺序，v3 | 43.293 | 0 | 仍为空方案，质量失败 |
| 紧凑枚举，v4 | 87.557 | 4 | 完整接收，0 禁用；仍有诱导性执行步骤与重复技能建议 |
| 同一 v4 再次请求 | 85.415 | 5 | 接收 4 条，重复询问已知方向的 1 条被禁用 |
| 已知方向限制与中性执行步骤，v5 | 70.751 | 6 | 维度引用不存在地址，整份拒绝；schema 通过不等于业务通过 |
| 引用绑定初版，v6 | 71.171 | 6 | 本次完整接收；绑定遗漏间接 `$ref` 的回归未通过，不计作最终版本验收 |

联合 schema 两次输出空方案，与紧凑 schema 的表现不同，但这不足以证明具体由模型、兼容通道或约束解码的哪一环节造成。最终采用紧凑 schema 是本次实测后的工程选择。

最终请求用量：输入 3,136，输出 2,757，合计 5,893 tokens。后端 115 秒、前端 120 秒预算保持不变；本轮耗时不能作为未来延迟保证。

## 内容质量仍有的不足

最终输出正确关注了 30% 的分母和统计口径；确认步骤未再列“透视汇总”等未证实的方法，也未生成替换简历的参考句子。但仍有以下人工观察：

- 技能区已有“Excel基础筛选与统计”，模型仍提出 `skill_create` 新增 Excel，属于冗余判断。
- 五条方案都进入事实确认，没有提供足够的已有事实组织方案；个人总结仍偏向不必要的追问。
- 在读状态、角色和方法等信息的追问必要性与覆盖仍需更多材料验证。

这些是内容判断问题，不应以 JSON 通过、零禁用或简历评分证明已经解决。当前没有添加语义正则拦截，也没有自动执行这些建议。
