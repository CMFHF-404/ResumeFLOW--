# GPT-5.6 Luna 与 Gemini Flash Lite 报告对照

## 范围与配置

使用原A/B/C/D四份冻结开发样本；同一 `resume_review_prompt_v8`、`review_json_schema_v5`、18项量表及服务端校验。两个型号均请求medium，评分后端预算115秒，前端等待上限120秒。没有改动默认Gemini模型、生产配置、用户简历或共享资料。

准确模型名称为 `gpt-5.6-luna`。官方模型页列明medium与结构化输出支持；当前配置的wolfai.top模型列表也包含该ID。独立最小格式探针在3.211秒返回HTTP 200、模型回显 `gpt-5.6-luna` 及正确的JSON对象。探针没有简历数据，不计入质量样本。

来源：[官方模型说明](https://developers.openai.com/api/docs/models/gpt-5.6-luna)、[结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs)。

本次比较的是当前服务路径与应用协议下的输出，不是独立于服务商、传输方式的模型通用能力排名。样本为开发集，复核者是本任务助手，未进行双HR盲评。

## 首轮结果

| 样本 | Gemini：耗时 / 可用报告 | Luna：耗时 / 可用报告 |
|---|---|---|
| A 数据分析 | 25.672秒 / 成功 | 86.804秒 / Markdown，协议失败 |
| B 经济学与研究 | 28.953秒 / 成功 | 74.566秒 / Markdown，协议失败 |
| C 银行财务 | 21.685秒 / 成功 | 57.798秒 / Markdown，协议失败 |
| D LLM技术 | 27.036秒 / 成功 | 86.847秒 / Markdown，协议失败 |

Gemini为4/4成功；Luna为0/4形成可用协议报告。Luna返回了完整正文，不是输出截断；首轮没有将Markdown转换为成功报告，也没有增加修复模型调用。Luna正文中的自由匹配分不能与服务端六维质量分直接比较。

首轮存在已识别的格式条件差异：Gemini请求带原生JSON schema，现有GPT Chat Completions路径只带同一提示词和输出示例。因此没有仅凭首轮0/4就认定Luna内在能力更差，另做了原生结构约束验证。

## 补齐结构约束

隔离测试脚本给Luna加入Chat Completions `response_format=json_schema`，使用相同schema语义并移除Gemini专用propertyOrdering；不改变提示词与样本，不增加单次评分调用数。

- 非严格schema模式：A在115.018秒超时，B在115.008秒超时；随后按原实验熔断规则将C/D标为未运行，不能算作模型成功或漏检。
- 另用D样本验证严格schema模式，也在115.022秒超时；结果单独保存在 `luna-strict-D`，不与首轮拼接成一次完整成功运行。
- 这些结果仅说明本次接入配置尚未在120秒等待目标内稳定形成可用报告。不能从超时推断模型没有生成内容、没有token消耗，或确定延迟全部来自模型推理。

## 内容质量的初步比较

以下Luna观察来自**未通过协议的原始Markdown**，只说明点评倾向，不代表产品已生成可执行方案。

| 关注点 | 本轮观察 |
|---|---|
| 信息取舍 | Luna对岗位版本、项目排序、低相关校园经历、证书荣誉取舍的展开较全面；Gemini也能给出课程筛选、隐藏及排序操作。 |
| 技术表达策略 | Luna对两个技术项目都给了具体的段落组织与压缩思路；Gemini主要覆盖RL项目的分层，另一项目偏向询问参赛/验收。Luna在这一点上有优势迹象。 |
| 专业证据 | 未显示Luna全面领先。Gemini的B样本较具体地追问研究问题、计量方法和结论；Luna也仍会把篇数、字数等工作量作为说服力，不能等同研究价值。 |
| 指标审阅 | Luna提出16K长度含义与部署复现条件，但又重复索要D已给出的样本规模和评测方式；Gemini仍把多基线对照称为严密消融。两者都未稳定补齐关键口径。 |
| 事实与能力边界 | Luna明显不足：B直接示范增加XLOOKUP、稳健性检验等未确认能力；D因项目复杂而认为“基础/了解”低估能力，并给出替换技能段落。附加“需确保真实”不能替代逐项事实确认。 |
| 日期与经历性质 | Gemini仍有把2026年4–8月实习误判为日期风险的情况；Luna的C改写示例把单日期竞赛写成持续“至今”，也不可靠。 |
| 输出与执行 | Luna大量返回整段参考改写，违背当前只给点评与修改策略的产品选择；首轮无可验证目标、六维档位和事实确认协议，不能直接勾选执行。Gemini形成了结构化报告，但结构通过不等于内容正确。 |

结论：**Luna更愿意展开修改思路，尤其是技术表达；但目前没有证据表明它在整体质量、事实约束和可执行性上更好，不宜直接替换默认模型。** 先解决其结构化报告接入与事实边界，再考虑独立同条件复测。不能用更长的正文、更多建议或更高自由分数代替质量验收。

## 工程与证据

为测试增加了两项入口保护：非Gemini评分仅在原生reasoning_effort与请求档位一致时允许medium；显式请求型号与实际解析路由不一致时提前拒绝，防止Gemini优先配置下静默换回Gemini。评分默认配置仍为 `gemini_primary / gemini-3.5-flash-lite / medium`。

相关后端29项回归通过，覆盖单次请求、显式型号匹配、medium原生参数、拒绝未支持档位、超时与历史兼容。原生JSON适配器只存在于隔离实验脚本，未接入生产默认路径。

全部原始输出、失败、用量及冻结哈希保存在 `.artifacts/evidence-luna-comparison-20260912/`：

- `comparison-protocol.json`：检查点及比较边界。
- `gemini-1/`、`luna-1/`：各四份首轮原始记录。
- `luna-native-1/`：非严格JSON schema实验及熔断后的未运行记录。
- `luna-strict-D/`：D的严格schema单独验证。
- `luna-canary.json`：最小能力与型号回显探针。
- `run_luna_native.py`、`run_luna_strict.py`：只在子进程覆盖路由的可复现脚本；各adapter-manifest记录其哈希。
