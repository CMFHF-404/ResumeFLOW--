# 简历报告减负与60秒截止（开发验证）

> 后续调整：用户已将等待上限放宽为120秒，当前前端截止为120秒、后端评分预算为115秒，预留5秒用于传输与校验。减负提示词、模型及medium设置保留。下文60/55秒参数和耗时数据是调整前的历史实验，不代表新一轮实测。

当前实现：`resume_score_v4 / evidence_rubric_v2`，`resume_review_prompt_v8 / review_json_schema_v5`，优化继续使用 `json_structure_v3`。模型固定 `gemini-3.5-flash-lite / medium`。灰度默认关闭，本次没有切换真实账户的评分版本或修改账户简历。

## 本轮改动

- 不再要求模型返回45–46项逐对象检查回执，也不返回每段经历重复的表达三项、指标五项记录。
- 保留18项原量表、原权重与服务端计算；每项仅返回档位、简短依据和必要的内部来源ID。删除锚点ID复写、未满足条件列表、高档与诊断之间的交叉解释要求。
- 审阅重点仍覆盖信息取舍、个人贡献、专业证据、技能边界、文本组织与评测口径。模型直接形成用户可选择的修改方案，不以固定建议数量或每类必出问题作为门槛。
- 策略分类和执行动作由程序根据已知目标及事实处理方式生成；模型不再重复填写这两个枚举。技能文字变更仍必须由本人确认；省略技能动作只进入保守的确认流程，不能升级程度或新增推断工具。
- 保留结构、档位、来源、选中对象及写入范围校验，以及现有事实确认、保存冲突、账户隔离、HTML清理、预览及撤销。技能候选仍须来自原文，未知来源不放行。不添加语义正则或二次模型审核。
- 历史报告仍按原协议读取；旧方案沿用原应用及撤销逻辑。新优化入口要求当前schema v5。没有伪造“全部已检查”的覆盖记录。

提示词从21,208字符减至6,452字符（约减少70%）。在相同JSON序列化口径下，A/B/C/D输入分别从35,513/49,671/59,216/26,368字符减至21,510/30,848/37,923/14,913字符。完整可见正文、教育、技能与证书数据保持不变；删除的是重复的目录和回执要求。字符数不等于token数。

## 截止行为

服务端评分调用最多55秒，前端整个评分操作最多60秒，包含评分前账户校验、请求与返回后的账户校验。服务层另有60秒保护，供非编辑器调用使用。用户取消与超时分别显示；超时后取消在途请求，不自动重试、不产生修复调用，迟到结果不能保存或污染新请求。

修复了 `AiRuntimeTimeoutError` 继承 `ValueError` 而被错误包装为“JSON无效”的问题。有效旧报告保留；其他AI功能的全局超时预算没有调整。

60秒是成功或明确失败的等待边界，不能保证上游网络异常时仍生成成功报告。测试覆盖了挂起请求被取消、账户校验挂起、模型返回后账户校验挂起、用户取消，以及迟到结果不保存。

## 建议质量与剩余问题

已经出现有效的课程筛选、数学建模竞赛前置、科研问题与方法追问、弱相关经历隐藏、财务段落分层、原文已有工具确认后创建等方案。相较之前耗时很长、最终仅少量建议的结果，减少回执没有让这些能力全部丢失。

仍然不能认定“大部分审阅质量已得到保证”：

- D的RL正文分层策略在run-6出现，run-7又漏掉；两个主要项目的表达策略并未稳定齐全。
- RL指标含义、比较条件及Judge核查方法仍不足。部分亮点将多基线对照直接称为严密消融，证据解释有越界。
- run-6 B的一条建议描述应隐藏CET-4，实际目标却绑定CET-6；虽然是可恢复的当前简历选择变化，仍属于重要方案定位错误。
- run-6 C把2026年6–7月实习误判为与2026-09-12评估日期冲突。评估日期确实已传入，属于判断错误。
- 少数追问方向仍给出倾向性示例，例如论文作者位次。原文不足时应保持中性。
- run-7 B因技能创建所需原文信息不完整而未形成报告，成功率尚未达到可正式启用的水平。

本次没有重新完成27+11个检查点的逐项独立标注，不报告虚构的覆盖率，不将可选数量或六维得分当作质量通过依据。继续保持灰度关闭；32份样本、双HR独立验收仍未完成。
