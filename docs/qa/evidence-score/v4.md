# v4 模块审阅与证据判档

协议 `resume_score_v4`，量表 `evidence_rubric_v2`，提示词 `resume_review_prompt_v7`，阅读视图 `visible_reading_v1`，岗位指南 `early_career_roles_v5`，输出结构 `review_json_schema_v4`。

当前默认请求档位为 **medium**。验收以建议覆盖、针对性与可执行性为主；分数极差、字段等价分差、纯润色提分和梯度排序保留为观察指标，不再单独阻止验收。足够多指覆盖有价值的问题与策略，不设无条件的建议条数下限，也不为凑数制造缺陷。

## 当前报告以可执行方案为主

按用户最新要求，报告顺序调整为简短结论、逐项可勾选的修改方案、值得保留、可展开的六维评分说明。可执行方案按优先级排列，每项说明问题、影响、修改方案及处理步骤；同一模块的不同方案可以独立勾选。执行入口只提交实际选中的可写建议ID，事实确认仍在选中后的流程进行。

报告不展示原文引用、来源路径、片段清单或独立审阅记录，也不重复展示项目策略与行动清单。`sources`、`evidenceSpans`、`expressionPlan`、`metricReview`等内部结构仍保留用于定位、校验及范围控制，不删除或伪造引用。手动建议另行折叠，不能通过前端勾选绕过服务端权限。历史v2阅读和按模块选择保留。

本轮桌面与移动端组件验证覆盖逐项勾选、优先级、手动范围、过期报告禁用，以及展开所有说明后仍不出现内部原文。只完成展示与提示词调整，没有新增真实模型验收结果；先前的超时和质量未通过结论仍有效。

## 实现行为

- 服务端以原文顺序合并非空经历正文，保留每段的原始引用地址。技术字段、空STAR槽位不作为内容要求；单日期由模型结合事件性质判断，不能仅因缺 `end_date` 扣分。
- 目录包含求职定位、逐条教育、学术证据、每段经历的贡献/结果/取舍、荣誉资质、技能、表达、时间和阅读顺序。`reviewChecks` 必须覆盖整个目录，给出非空依据并引用检查对象；可同时引用其他模块作为比较上下文。`findings` 关联诊断，`clear/not_applicable` 不关联诊断；诊断不能脱离审阅项。
- 八主题概览状态由已校验的逐项结果汇总，避免概览称“无需修改”而对应模块仍列出问题。
- 18个观察项分别具有五档标准、正例和反例，保存在 `backend/app/domain/ai/evidence_anchors_v2.json`。档位由模型选择，权重与整数舍入保持原规则，无总分封顶或额外扣分。每项必须给出匹配档位的 `anchorId`，低于4档需说明至少一个更高档未满足条件；高档关联高优先级问题时需解释原因。
- 每个诊断关联一个 `primaryCriterionId`。`factGaps` 提供中性问题，`handling` 区分已有事实整理、询问用户、手动核查。`needsFacts` 由事实缺口数量计算。规划器只引用评分时已有的 `gapId`，由程序还原原问题，不另编引导问题。保留一次评分、一次所选模块规划、最多一次回答后批量改写。
- 数据分析和行业研究指南补齐课程/科研亮点、研究问题与方法、结论与使用方的审阅；银行财务指南强调核算、异常处理和财务数字化，不把企业经历改成银行业务。
- 没有方向与JD时固定提示“尚未提供求职方向，本次为通用内容评估”，不自动扣分。

### 本轮建议与结构约束

- 每段经历新增叙述主线和评测口径检查，增加可安全展示的成果/复现材料检查；奖项检查范围包含技能和总结中已有的荣誉、语言信息。
- Gemini 单次评分携带原生 JSON Schema，限定模块、来源、固定检查项、18项观察项、档位及条件标识。生成顺序为逐项检查、建议、档位、结论，避免先输出总评；这只是实现选择，效果以真实输出为准。沿用结构/引用校验，不做内容正则门禁或额外模型审核。
- 新建议包含 `recommendationKind=fix/enhance` 和 `strategySteps`。可选增强只标低优先级，不作为程序额外扣分；界面区分“需要改进”和“可选增强”，可展开执行步骤。
- 模型只选择 `factGaps.kind`、补充原因与来源，程序根据固定模板生成问题；优化规划仍引用已有 `gapId`。技能动作说明由程序生成，技能文字与分类经用户逐项确认后组合为当前简历覆盖值；其余自由文本仍由模型生成，相关事实错误须纳入质量记录。
- 原生结构采用 [Gemini 官方结构化输出](https://ai.google.dev/gemini-api/docs/structured-output) 的 `$defs/$ref`、`prefixItems`、枚举和 `anyOf`。不支持该结构的通道明确返回失败，不自动请求修复。

## 配置与历史兼容

v4默认关闭，需要已有证据评分总开关和v4开关同时打开：

```text
ENABLE_EVIDENCE_RESUME_SCORE=true
ENABLE_RESUME_REVIEW_V4=true
VITE_ENABLE_EVIDENCE_RESUME_SCORE=true
VITE_ENABLE_RESUME_REVIEW_V4=true
```

前端两项均为构建变量，根Dockerfile已透传。`RESUME_SCORE_MODEL` 默认 `gemini-3.5-flash-lite`，本轮只使用此型号；`RESUME_SCORE_THINKING_LEVEL` 默认 `medium`，仍可显式覆盖。这两个配置只影响v4评分，其他AI功能和v3基线不受影响。模型覆盖必须是同通道中实际可用的型号；不自动切换提供方。非Gemini通道不支持本轮 `medium/high` 覆盖时明确失败，不静默忽略。

v2/v3/v4报告按各自协议读取，不转换历史分数。新优化需匹配当前启用版本；v4还需 `review_json_schema_v4`。较早v4报告仍可阅读，但需重新评分才能生成新方案。旧方案仍可读取、应用、撤销。关闭v4开关可退回v3，关闭总开关退回v2；报告阅读不受开关影响。

正式切换须核对服务新进程和返回的版本，不能以“出现热重载日志”替代。先前本地调试出现过旧进程未退出的情况。该迭代不自动更新运行环境或生产开关。

## 冻结开发实验

原三份HR样本、旧输入及全部旧输出留在 `.artifacts/evidence-hr-compare-20260912/`，不会覆盖。校对后的开发输入位于 `.artifacts/evidence-v4-dev/`：去掉人为添加的分区标题前缀；图3使用已记录的转写敏感性版本。原稿教育备注等被保留为评分服务可读信息，并不代表编辑器导入流程能够无损生成相同快照。开发样本不得作为独立盲测。

从 `backend/` 使用独立工具；每个输出目录只能创建一次：

```powershell
python -B evaluate_resume_review_v4.py freeze ../.artifacts/evidence-v4-dev --output ../.artifacts/evidence-v4-experiment/input-manifest.json --equivalent
python -B evaluate_resume_review_v4.py run ../.artifacts/evidence-v4-experiment/input-manifest.json --output ../.artifacts/evidence-v4-experiment/run-1 --live --profiles low medium high --repeat 3
python -B evaluate_resume_review_v4.py summarize ../.artifacts/evidence-v4-experiment/run-1
```

该命令执行3个原始开发输入加1个字段等价输入，每档各3次，共36次单次模型调用。每次调用独立保存成功或失败；记录输入hash、提示词/代码/量表hash、请求档位、耗时、usage。等价版本把第一份样本所有非空正文按原顺序移到同一字段，不改事实。实验期间不改提示词或丢弃失败成员。

运行器在某档位连续两次超时时停止该档位尚未发起的成员，明确写入 `not_run`；在途请求保留各自结果。未发起成员不计为耗时0秒的成功样本，也不计入耗时统计；任何失败或未完成都会使该配置不合格。每次发起前另外保存开始记录，便于识别外部中止留下的在途成员。

汇总报告列出各样本分数及极差、配对等价分差、主要诊断集合的Jaccard一致性、P95耗时与用量。Jaccard按模块和主要观察项形成诊断键，是一致性代理，不声称语义完全相同。没有对照标签时，不选择质量合格配置。

后续未指定 `--profiles` 时仅运行medium；上面的显式三档命令仍可用于对照。新增建议数量、覆盖模块数和策略类型分布，均为观察指标。分数波动不再影响候选资格，模型请求失败、漏检、空泛建议和编造事实仍需处理。

可通过 `--labels` 输入经复核的开发集覆盖、误报、严重错误计数，文件必须绑定本次 `run-manifest.json` 的SHA-256：

```json
{
  "runManifestHash": "本次运行清单的SHA-256",
  "profiles": {
    "low": {
      "completeCheckpoints": 0,
      "checkpointCount": 27,
      "falsePositives": 0,
      "reviewedDiagnostics": 0,
      "actionableDiagnostics": 0,
      "severeErrors": 0
    }
  }
}
```

计数必须来自逐项对照记录，示例零值不是标注。`actionableDiagnostics` 计入明确说明改哪里、如何改或需要确认什么事实的建议，不计泛泛点评和重复凑数。开发候选需覆盖至少22/27项、诊断准确率及建议可执行率均至少90%、无严重错误且运行完整。工具仍输出满足质量要求候选中的P95最低者供参考，应用默认档位由配置明确设为medium，不由工具自动更改。生产仍需独立人审。

## 独立质量验收

`evaluate_evidence_score.py scaffold` 的新清单版本为2：产品、技术、财务、运营各4份，数据分析和行业研究各8份，共32份；每方向覆盖应届/初级社招，开发与留出各16份，同源A/B/C/D变体不跨组。旧版四方向清单仍可读取。作者确认、双HR独立标注和分歧处理要求不变。

真实提供方运行示例：

```powershell
python -B evaluate_evidence_score.py run <manifest.json> --version v4 --thinking-level medium --split holdout --live --output <new-results.jsonl>
```

没有真实样本和双HR标注时，只能报告工程、开发集表现，不能宣布建议质量达标。正式验收保留高优先级召回/准确率≥90%、来源正确率≥95%、建议可执行率≥90%、误改保留内容≤5%及严重错误为零。评分相关指标仅作辅助观察。
