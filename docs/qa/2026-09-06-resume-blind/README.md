# 六维评价与优化真实模型盲测

本次使用虚构的 B2B SaaS 产品经理 JD 和四份合成简历。所有人名、组织和经历均为测试数据。测试目标是检查分档、重复评分波动、明显瑕疵定位、优化后的实际修复与分数变化。

## 预先固定的方法

- 三个质量档次，另加一份“来源事实充足、当前表述退化”的对照样本。
- 每份原文评分三次；取编号最小的成功报告生成两次独立优化，不挑最高分或最佳方案。
- 首个成功优化的结果重复评分三次；只组装通过现有规则和真实 AI 语义审核的通用候选。
- 补充问题统一回答“没有额外可确认的数据”。来源中已有事实仍可引用。
- 质量标签和预设瑕疵单独保存在 `key-*.json`，不传给评价或优化模型。
- 盲评员以独立调用接收随机编号及打乱顺序的正文，不接收分数、质量标签和前后版本身份。沿用已配置模型，因此属于同模型独立调用盲评，不是跨模型或外部人工盲评。
- 预设稳定性门槛：三次总分极差不超过 5 分，各维度极差不超过 10 分。这是本次工程验收阈值，不是统计学显著性标准。
- 保留失败、超时和被拦截的方案，不能只报告成功案例。

## 证据范围

调用生产实现的评价、优化规划、回答改写、事实规则检查、语义审核和计费服务，使用真实提供方回复。没有 mock、替换 AI 输出或放宽安全校验。

服务层测试直接构造冻结上下文并组装审核通过的候选，**不等同于**验证 HTTP start/apply/finalize、前端保存协调和 OAuth 登录。网页登录测试身份需要用户完成注册；内部测试身份 `qa-blind-20260906` 没有登录凭证，不是管理员。

数据库仅允许 `localhost/resumeflow`，内部测试身份授予 30 天不限量权益；供应商实际用量仍正常记录。样本同时以正式简历/经历记录保存到该内部身份下，便于后续检查。

## 重现与文件

从 `backend/` 运行：

```powershell
python qa_resume_blind_benchmark.py prepare --run-tag NEW_TAG
python -u qa_resume_blind_benchmark.py run --run-tag NEW_TAG --user-id qa-blind-20260906
python qa_resume_blind_benchmark.py summarize --run-tag NEW_TAG
```

将 `NEW_TAG` 替换为未使用的纯字母数字标签（例如 `review20260907`），三条命令使用相同标签。输出位于 `docs/qa/2026-09-06-resume-blind-<标签>/`。

`prepare` 会冻结语料、协议、脚本和运行配置；相同内容可重复执行。共享 `run()` 在任何记录写入、数据库操作和缓存读取前重新验证清单，验证通过后才复用已完成的调用记录，包括失败记录。模型、代码或输入变化，以及旧目录缺少完整清单时，必须使用新标签；不要清除失败记录或覆盖历史证据来改善成功率。运行创建时间记录在 `run-manifest.json` 中。

直接采用扩展使用 `python qa_resume_blind_direct.py NEW_TAG`，读取原始目录的合成语料，写入独立的 `2026-09-06-resume-blind-direct-<标签>/`。它重新生成当前评分版本的三次基线，取编号最小的成功报告，不读取历史基线分数；代码、语料、协议和运行配置均通过冻结清单校验后才能续跑。该扩展沿用已有本地测试账号，不创建账号或授予权益。共享 `call_record()` 和独立诊断入口均在计费与模型调用前检查本地数据库限制。

- `fixtures.json`：JD、匿名样本及同经历的来源版本。
- `protocol.json`：执行前固定的阈值与选择策略。
- `environment.json`：模型配置与脚本、样本、优化服务源码哈希。
- `baseline-*.json` / `post-*.json`：逐次真实评价及耗时。
- `optimization-*.json`：计划、回答、审核结果、被采用条目和候选正文。
- `blind-judge-input.json` / `blind-judge.json`：独立盲评输入与输出。
- `blind-judge-key.json`：揭盲映射，仅用于评测结束后的解释。
- `summary.json`：分数均值、极差、标准差和维度波动。

本次每个档次只有一个样本，不支持泛化到所有岗位和所有简历；同样，模型审核只能判断是否忠于给定资料，不能证明经历在现实世界中真实发生。
